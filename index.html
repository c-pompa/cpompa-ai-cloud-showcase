Metering demo — how units are priced

One unit is the measured serving cost of one chat turn on the small model. Every user gets $1/mo Starter with 500 free units; usage beyond that is bought as top-ups at the same published rate — $1 = 2,000 units. No request caps, no 5-hour windows. Drag the slider:

Margin is nearly flat across every shape (71.5%–74.8%) because the meter follows cost — routing to a bigger model is a priced decision, never a silent loss.

Why meter in units instead of requests?

A chat user makes one call per message. An agent task makes dozens — a single "summarise these invoices" run is a planning call, five tool calls, two retries and a synthesis (30–100 LLM requests). Metering the call charges customers for our implementation detail; that's why per-request allowances look generous in a demo and evaporate in a week of real agent use. The unit is the honest atom: it maps to what a request actually costs us, weighted by model size and context length.

Benefit to the company

  • Predictable, near-flat margin (~70%) at every request shape — revenue scales 1:1 with measured serving cost, so no surprise loss from heavy tenants.
  • Heavy users pay proportionally. Usage beyond the grant flows into top-ups at the same rate — expansion revenue without changing plans.
  • Priced routing. Serving a 27B agent turn costs 67× a small chat turn; the unit weights that automatically, so model mix is a margin decision, not a leak.
  • Test-enforced billing integrity — the rate table is generated from measurements and a CI test pins the meter to it.

Benefit to users

  • Transparent and predictable: you pay for tokens you actually use at a published rate, not a black-box credit system or 5-hour refresh windows.
  • Agents are affordable: no per-request caps means an agent that makes 50 calls for one task pays for the tokens, not 50 "premium requests."
  • Try-before-you-scale: 500 units free every month covers roughly 500 chat turns — real evaluation before spending a cent.
  • Per-workload fairness: light chat users aren't subsidizing heavy coding-agent users; each workload is charged by its own cost.

Why it's a good growth strategy

  • Land below the market floor. Market entry has converged at $20/mo (Claude Pro, ChatGPT Plus, Cursor). Entering at $1/mo is a 20× lower commitment — trivially easy to try, and paid users validate demand from day one.
  • Usage-led expansion, not upsell friction. Growth happens automatically as users consume more top-ups — the pricing curve grows with the customer instead of forcing plan migrations.
  • Agents are the growth engine. Agent workloads consume 30–100 requests per task, so adoption of agentic tooling directly multiplies unit consumption — and the unit meter captures all of it fairly.
  • Margin-proof to model deflation. Because rates are derived from our measured hardware cost, we can re-derive prices as models and hardware change — the same property commodity API resellers (who rent compute) can't match.
